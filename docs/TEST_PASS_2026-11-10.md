## The main limit: menu buttons can't be pressed in a hidden test game

Assistant Access can read the whole menu (`gucci_ui`) and change saved switches for one launch (`gucci_test_set`), but it has nothing that presses a menu button. Two workarounds failed:
- **A touch through GD's dispatcher** (`gucci_ui_tap action=touch`) never moves ImGui's mouse on Windows. imgui-cocos only takes a touch's position when `getMousePos()` is zero, and on Windows it's never zero: a window the mouse never crossed reads as (0, 320).
- **Mouse messages posted to the minimized window** (WM_MOUSEMOVE, WM_LBUTTONDOWN/UP) didn't highlight or press anything either.

So every item that needs a button press (Save, Rename, Convert, Render, Reorder...) is listed below as not tested. A test tool that presses a menu control by its gucci_ui id would cover all of them next time.

## Bugs found (not fixed here)

1. **Mute during Calculate leaves the game silent.** With the switch on, music and SFX volume stay at 0 after the run ends. The analyzer always mutes on its own (`FrameWindowAnalyzer::muteAudio`, src/analysis/ac/framewindow.cpp, at the start of a run). The switch then mutes a second time (`GucciEngine::muteAnalysisMusic`, src/core/engine_core.cpp), which saves the already-0 volumes. At the end the analyzer puts 1 back, and the switch's unmute puts 0 back over it. (The test save's CCGameManager.dat still says 1 / 1: the test launch didn't write it.)
2. **Macros with one name under several themes all show one theme.** zz_gbtest_tp_tag.juice, .solar and .rondo were listed three times, each as .solar / SolarBot, and the three rows share one ImGui id (0x4F6FB127). The row's extension comes from `storedMacroExts`, which is keyed by name (src/ui/shell.cpp, around line 3707). So a click on one row may act on another.
3. **The "No death flash" log line never shows.** The flash is hidden, but `[GucciBot] No death flash: the death added [...]; N hidden` (src/hooks/hook_playlayer.cpp:95) wasn't in Geode's log after two deaths. Other GucciBot lines from the same minutes were. I'm not sure why. The POLISH_ROUND decision 7 note asks Nigel to read that line, so it matters.
4. **Calculate floods Geode's log.** A 9-input Calculate run wrote about 6,300 lines: `[trailbuf] killed at frame...` WARN 2,628 times and `[fw][restore]` 3,630 times, up to 1,500 lines a second. Item 126 only covered playback and renders, and those are clean now.

### Bugs found in part 2 (not fixed here)

1. **The in-render HUD always says 0 frames.** `SLRenderer::m_frameCount` (src/render/renderer.hpp) is set to 0 when a render starts (renderer.cpp:604), and nothing ever adds to it. `renderedFrames()` returns it, so the Render card shows "0 frames, N s of the level so far" for the whole render.
2. **A Showcase (RGB) render plays back in the wrong colors.** With libx264rgb and rgb24, the file is tagged `yuv444p(tv, bt709)`, and when decoded it shows a teal background and a green ground. I'm not sure of the cause. One possibility: the renderer tags every stream as BT.709 limited-range YUV (color_primaries, colorspace and color_range, renderer.cpp around line 459), but an RGB stream needs the RGB tag, so players convert it as if it were YUV. Only BlueStacks' FFmpeg 4.4 decoded it here; a player on Nigel's PC should be checked too.
3. **Record from Off, with a macro still loaded, drops your clicks.** Paused at frame 0 after a restart, with a 10-input macro loaded and Mode Off, I chose Record in the menu and played: nothing was recorded, and the old 10 inputs stayed. addInputToReplay (src/hooks/hook_gjbasegamelayer.cpp:340) skips an input that comes before the macro's last action, and starting Record from Off doesn't clear the old macro. Only a restart or a death does. Restarting after choosing Record records normally.
4. **guccibot_fw.log never gets smaller.** It's opened for appending, with a "new session" banner, and is never trimmed (src/analysis/ac/framewindow.cpp:50). Since -k, every Calculate run's detail goes there (20,407 lines for this 5-input run), and the test save's copy is 101 MB, 903,000 lines. Each line is also flushed on its own.
5. **Every backup is `<name>.brrr.bak`, whatever the theme.** `backupExisting` (src/core/engine_core.cpp:651) replaces the extension with .brrr.bak, so backups of zz.juice and zz.solar would overwrite each other. This is minor, but it's the same name-versus-file mix-up as part 1's bug 2.

## Follow-up: part 2's five bugs (same morning, builds -n to -z, tested in the gdcopy_sync copy)

Each fix had its own build, was tested in the test copy, and was then reviewed. The review sent six of them back, and the second round (-u to -z) is what ships. Part 3 retested most of them on -ab.

1. **Fixed in -n, hint reworded in -x.** The HUD now reads the encode thread's count of frames written. That count was also never reset between renders: from the second render on, the ring's room check always passed, so a slow encoder could have a frame's slot reused before it read it (found by reading the code, never seen in a video). It is reset at each start now. Two renders back to back: the HUD counted from 322 to 1441 frames, then started again and reached 1480, and FFmpeg counts 1449 and 1488 frames in the files. Since -x the hint says "{n} frames written (the intro card's too), {t} s of the level so far", because the frame count includes the intro card and the seconds don't. Part 3 (on -ab): 1536 frames = 51.2 s, the 46.2 s of level plus the 5 s intro.
2. **Fixed in -r, narrowed in -w.** An RGB stream is now tagged RGB, full range. A Showcase file reads as gbrp(pc, gbr/bt709/bt709), and its background and ground match the yuv420p render and an in-game screenshot ((38,34,168) against (38,34,168); no teal, no green ground). The review found that -r also tagged rgb0 as RGB, but the encoders that take rgb0 (NVENC, AMF) turn it into YUV themselves. Since -w the tag follows the stream: only RGB input to a software encoder gets it. Part 3 (on -ab): an rgb0 render through AMF came out yuv420p, tv range, BT.709, with the right colors, and Showcase's background was (22,70,144) against nv12's (23,72,146). An rgb0 render through NVENC hasn't been made (this PC has no NVIDIA card).
3. **Fixed in -o, then changed in -u.** -o kept the macro up to the current frame, as Play to Record does. The review found that wrong above frame 0: in Off nothing of the macro played, so the kept part was old clicks spliced onto a run that didn't make them (the -o test itself kept 6 actions from an earlier attempt). Since -u, Record from Off with a macro loaded drops that macro and starts a fresh recording from the current frame. A button held at the switch is recorded as pressed on the first recorded frame. On Stereo Madness: at frame 0, 10 old actions dropped and 3 clicks recorded; at frame 215, 0 kept and a click recorded at 222/242; Play to Record at frame 119 still kept exactly the 4 actions played. Part 3 (on -ab): Off to Record at frame 1000 went from 20 actions to 0, and Play to Record at 1000 kept 201, 221, 801 and 821.
4. **Fixed in -p, then -v.** guccibot_fw.log now starts fresh on each launch's first fw line, and the launch before's log is kept as guccibot_fw.old.log.
