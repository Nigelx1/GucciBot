# In-game test pass, 2026-11-18

Claude's unattended test of what was still "built, untested" in docs/ROAD_TO_2_0.md, run in the morning of 2026-11-18 while Nigel was at school, ahead of the Thursday 11-19 code freeze. Five groups ran at once, each in its own hidden test copy.

- **Build:** 2026-11-18-h, master at 5420388 (HEAD 63646cb is a docs-only commit on top of it).
  - GD 2.2081 copies: the main repo's build\nigelx1.guccibot.geode, md5 25fcab2408d61b85b3d7d49df00244ef, checked again before each install. Every launch's `gucci_get_state` reported `2026-11-18-h (Frame Editor: Escape pauses a running level even with a bar selected)`, version 2.0.0-beta.5.
  - GD 2.2091 copy: master 63646cb built for GD 2.2091 + Geode 6.0.0-alpha.2 in a worktree at C:\gbwork\testpass1118 with port2209\g6_build.py ("Build complete", 278 s), md5 8046120e84eca5ce8673430109cfcf72, the same -h label in game. Geode's log: "Running Geode v6.0.0-alpha.2 in Geometry Dash v2.2091 on Windows".
- **Copies:** render (GDRender.exe), sweep (GDSweep.exe), pf2 (GDPf2.exe) and deco (GDDeco.exe), all GD 2.2081, and g6b (GD2209b.exe, GD 2.2091, a signed-out save). One game per copy at a time.
- **How it ran:** every game was started through the lanes' testcopy/assist tools: minimized, off screen, muted, BelowNormal priority, safe mode forced for that launch and checked. `sharp=True` (1850x1041, High textures) only where a shot had to look like Nigel's screen. Nigel's game, saves, settings and mods folder were never touched; his KOCMOC UNLEASHED New.brrr and two .ybot files from Downloads\Macro Dump were only read and copied in as test files. GD's Terms of Use box was never tapped. In g6b only Stereo Madness was opened, never an online level's page. The runs went from about 10:09 to 11:27, and every game was closed by then.
- **Test files:** all named zz_gbtest_tp18_* (plus the sweep copy's existing zz_gbtest_kocmoc), deleted afterward. Each copy's saved.json was put back byte-identical where a test wrote to it by hand (sweep, pf2, deco). Videos were deleted after reading.
- **Evidence** (in the scratchpad, lanes\testpass1118\): one write-up per group (render.md, sweep.md, pf2.md, deco.md, g6b.md), the running notes (PROGRESS.md), scripts and raw results (rwork\, sweep\, pf2\, deco_t\, g6b_t\), and the shots (shots\render, shots\sweep, shots\pf2, shots\deco, shots\g6b), each one looked at.

**Totals:** 45 checks: 32 PASS, 9 PARTIAL, 3 FAIL, 1 BLOCKED (and one step inside a PARTIAL blocked). Nothing was fixed here: this pass finds and records.

**The three FAILs:**
1. A render in Off mode with a macro loaded never stops at the level end (render X1).
2. The Leg trail stays drawn in the level after the run ends, even through a restart (sweep S6).
3. A real yBot macro (Nigel's Bloodbath.ybot) converts one frame off: it dies at 5% as converted and completes only with Shift frames +1 (pf2 P5a).

**Also found:** the test tool's screenshot briefly put a hidden game window on screen (g6b, below), and once a quit during a KOCMOC Calculate run hung the game and ran its memory to 40 GB (sweep S5, not reproduced).

## The FAILs and PARTIALs, with steps

### FAIL X1: a render in Off mode with a macro loaded never stops at the level end
Steps: load any macro (or record one, then set Mode to Off). Render > Seconds after the end 0, Start from the beginning, let the level finish.
What happened: GD's end screen shows and the render keeps writing end-screen frames until Stop is pressed. With a 4-action macro (frames 301 to 631, inside a 5 s level) it was still rendering at 26.1 s of level time; with a 16-action one it reached "23428 frames written, 390.5 s of the level so far" and 472 s (155.5 MB). No "Render stopping" line until Stop. In Play mode the same macro stopped with "Render stopping: the level ended (0 seconds after the end)" at 9.4 s.
Likely spot, by reading only: src/render/renderer.cpp around line 1420 treats the level as done only when `replay.getCurrentQueuedInput()` is empty, and that (engine_core.cpp:374) ignores the mode, so in Off mode the cursor never moves and the render can't end. The same check would hold a Play-mode render if a macro has inputs after the level's end. I'm not sure whether waiting for queued inputs in Play mode is Silicate's on purpose.

### FAIL S6: the Leg trail stays after the run
Steps: Calculate > Advanced > Show advanced settings, Leg trail on, KOCMOC range 400..600. After "Measured 2 of 2 inputs", restart the level and play to 590.
What happened: during the run each test run draws as described (yellow, green, red with an X, and the white capture line). After the run and a restart, the leg lines and an X are still drawn over normal playback. Expected: gone.
Likely spot: `FrameWindowAnalyzer::finish()` calls `dropLegTrail()` (src/analysis/ac/framewindow.cpp around 5122), which returns before removing the leg-trail nodes when `m_trailShown` is false (around 9878). I'm not sure that's the path that left them.

### FAIL P5a: Nigel's Bloodbath.ybot is one frame off after conversion
Steps: copy Downloads\Macro Dump\Bloodbath.ybot into replays as a test file, press its Convert under From other bots, play it on Bloodbath (10565740) from a restart.
What happened: 578 inputs, the original moved to replays/converted. As converted it dies at frame 1425 (5.03%); with Shift frames -1 at 1410 (4.95%); with Shift frames +1 it completes (frame 27926, Level Complete shot). So yBot counts frames one lower than GucciBot, as Silicate does.
Likely spot: src/tools/macro_convert.cpp, readYbot2 and its per-bot frame offset. This rests on one real file; I'm not sure every yBot version counts the same way.

### PARTIAL R3: render stop reasons
(a) gucci_restart_level and (b) gucci_practice are refused during a render ("render currently owns the run"), so the pause menu's Restart and Practice buttons were used; both passed. (d) is BLOCKED: gucci_open_level and gucci_open_level_string refuse while a level is open ("leave the level (or the editor) first"), so the "another level opened" stop is still unseen.

### PARTIAL S2: Manual Frame Windows
The Every input table's window cell is a bare `InputFloat("##w")` (src/ui/pages/calculate.cpp around 1272), and the UI probe drops items with no label, so a hidden test can't type into it. Everything after the typing was checked through the same set path (Apply label 5 on 420, and the table's Use on 5409). Typing into a row still needs Nigel, or a probe label on that box.

### PARTIAL S5: a failed run
Steps: KOCMOC range run, gucci_quit_level mid-run. The log says `[fw][finish] ok=false ... msg=Canceled.`: a quit is a cancel. Every window kept, but the .fwac is rewritten with the header's "measured" dropped from 400 to the cancelled run's 2 (minor; I'm not sure it's intended). No way to make a run fail from a hidden test was found.
**Seen once:** the first try, in a game up 19 minutes that had opened KOCMOC (199k objects) about 6 times, stopped answering right after the quit (fw log ends at "[fw][restore-macro] 2 action(s) still shifted at finish, all put back"), and its memory grew 14.6 GB -> 36.6 GB -> 40.1 GB in about a minute before it was killed (free RAM 0.4 GB, commit 91%). A retry in a fresh game quit cleanly in 1 s. Worth a repro: quitting a big level while Calculate puts the macro back.

### PARTIAL S7: time readout and the time-cap notice
1-minute cap, KOCMOC range 4800..6060 (44 inputs), sharp launch. Readouts: "0:10 so far, about 0:28 to go", "0:20 so far, about 0:10 to go", then in the probe stage only "0:30 / 0:41 / 0:51 so far" with no "to go" (the percent also starts over per stage). Stopped at 61 s keeping 7. The end notice wraps onto 3 lines that fit, but is cut off: "...Raise the cap (Calculate page, Speed), or press Continue from where it sto...". The same 3-line cut shows on S8's capture-death notice. The notice's "(Calculate page, Speed)" points at a section that only shows under Advanced > Show advanced settings.

### PARTIAL S11: the sub-tick counter
It counts every input, releases too (10 for 5 clicks); whether it should count clicks is Nigel's call. "Placed in the tick" can't be reached with gucci_click (no Windows input timestamp); it needs real clicks with Sub-tick clicks on.

### PARTIAL P1a: Faster sub-tick search
6957's sub-tick window came out 2.93 with the switch on against 2.80 off: the normal search found dead slots at -27 and -30, and the seeded bisect stepped over them to a live -39. That's the limit the code's comment describes ("a gap smaller than a frame inside a window can come out different"), so "sub-tick within a slot" fails by 13 slots there. The saving was 39% of the sub-tick test runs on the ship range and none on 400..600 (559 is a 1-frame window the seed can't narrow).

### PARTIAL P3: Mid-tick edges stay sub-tick
No KOCMOC input has a sub-tick count that comes to a whole number of frames (no "CBF adds nothing" or "N.010 frames" line in any KOCMOC log), so the switch's branch never ran, and the switch wasn't read back in the game. A real test needs a level that has such a count (Nigel's 647 run).

### PARTIAL D6: 1000 TPS pacing
Needs GD's FPS cap at 60 to bind the 10-a-frame cap; at this copy's ~360 FPS both settings run at full speed. A 5000 TPS probe was spoiled (noclip turned off by mistake) and isn't used.

### PARTIAL D10: Only while holding
The keyboard and player 2 halves pass. gucci_click without a key doesn't go through UILayer, so it isn't a real held mouse button: 0 autoclicker clicks, which says nothing. I'm not sure what a real mouse hold does.
